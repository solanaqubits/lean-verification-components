# Signed Byzantine broadcast: agreement and commander validity

[Section](../distributed/README.md) · [Lean](../../Verification/DistributedByzantineSignedGeneralsValidity.lean)

## Model and result

Parameters specify Fin n nodes, a commander, a static faulty set F with card F <= f,
a binary command, and f + 2 <= n. The commander is a parameter; the three-node
instances use node 0. HonestLieutenant excludes both the faulty set and commander.
The population condition is a scope restriction, not a necessary threshold for
signed broadcast. It guarantees at least two honest nodes: two honest lieutenants
when the commander is faulty, but potentially only one when the commander is honest.

The module formalizes a synchronous, round-indexed signed-chain implementation.
A state records the completed round, accumulated order sets, an issuance ledger,
and next-round outbound batches. In round r, acceptance requires a nonempty path
beginning with the commander, distinct signers and exactly r signatures. Accepted
orders accumulate by finite-set union. For a previously unknown order, each eligible
honest lieutenant appends its identity to each eligible received chain and forwards
the resulting chains to nodes outside the path, provided r <= f. Nodes already on
a path need not receive a new packet; their earlier signing supplies the propagation
witness. Decisions occur after f + 1 rounds: output 1 exactly for the singleton {1},
and retreat (0) otherwise. In particular, every singleton is decided correctly.

For every completed reachable execution, honest lieutenants have equal final order
sets and equal decisions. With an honest commander, each final honest lieutenant
view is exactly the singleton command. Every reachable nonterminal state can advance;
completed executions exist. This prevents a vacuous safety claim over no valid runs.

## Ideal signature semantics and operational provenance

SignedChain stores an order and an ordered signer list, but this syntax alone is
not a valid signature. Derivable is a separate inductive signature environment:
an empty payload is public; a faulty signer can append freely; an honest append
requires that the entire resulting signed prefix already belongs to the issuance
ledger. Each extension binds the order and preceding prefix. Honest signatures
enter the ledger only through initialization by an honest commander or a protocol
transition processing an accepted, previously unknown order.

Run is generated by these transitions. Delivery requires all honest outbound
messages to reach honest lieutenants and every delivered chain to be derivable
from the existing ledger. It assumes neither agreement nor propagation. Byzantine
senders may withhold, replay, delay and selectively deliver available signed chains.
Finite sets identify duplicate packets; the idempotence regression makes this
representation explicit. Faulty local views are not part of the correctness claim.

The provenance proof first extracts an issued prefix for any honest signer in a
message. It then derives an actual issuing transition with its accepted parent and
a valid continuation to the current state. For a non-commander, the receipt/signing
round equals the parent length. The honest commander is an explicit initial-signing
exception: it does not receive its own command. The ledger is an ideal issuance
model, not a proof of computational signature unforgeability.

## Inductive proof

Every issued order has reached each honest lieutenant or is in its mandatory
next-round mailbox. Pending chains satisfy the next round's length check. These
invariants follow from initialization and transitions. They imply that a known
order reaches all honest lieutenants by the end of the next round, including
recipients who already knew it.

A final-round chain has f + 1 distinct signers and F has at most f nodes. The
pigeonhole lemma supplies an honest signer; its issued prefix forces dissemination.
A second invariant applies this argument to all accumulated views. At the terminal
round no honest forwarding remains, so the views coincide. An honest commander's
signature can introduce only its original order, which every honest lieutenant
receives reliably in round 1; hence validity.

## Regressions and OM bridge

For n = 3, f = 1, an equivocating commander produces {0,1} at both honest
lieutenants after two rounds, and both retreat. A silent commander yields empty
views. An honest commander with a faulty lieutenant yields its singleton command.
The live kernel regression also instantiates f = 0, n = 2 and f = 2, n = 4.
Empty paths, repeated signers, a non-commander root and late short chains are rejected.

The late-message counterexample starts from a reachable silent first round. A faulty
commander reveals a valid one-signature order only to one lieutenant in round 2.
Keeping the shape/signature rules but dropping the final-round length check yields
decisions 1 and 0. The actual protocol rejects the packet and both retreat. Since
forwarding has already stopped in this final round, this isolates the receipt filter.

A bijection maps Fin 3 to the roles of module 144. The bridge combines its OM
impossibility with signed correctness for all three-node fault sets of size <= 1.
The wrong-root rejection theorem exposes the changed adversary capability. No
embedding of signed protocols into the unrestricted OM transition model is claimed.
Module 144 itself proves n = 3, f = 1, not the general n <= 3f lower bound.

## Clean Water boundaries

The result is an ideal-signature, deterministic synchronous broadcast theorem for
static membership and faults, with decisions at a common finite deadline. It does
not establish RSA/ECDSA/BLS security, signature serialization, computational
unforgeability, asynchronous behavior, dynamic corruption, network implementation
correctness or optimal round/message complexity. It is not an executable production
signature scheme. Python, JSON/SHA-256 and SimLab obligations remain open.
Only propext, Classical.choice and Quot.sound are permitted. Novelty is not assessed.

Reference: Lamport, Shostak and Pease (1982),
[The Byzantine Generals Problem](https://lamport.azurewebsites.net/pubs/byz.pdf).
The explicit round-length filter is part of this formalized round-indexed contract.
